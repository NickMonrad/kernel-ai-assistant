# Shared Lists sync contract

> **Purpose:** Canonical transport-independent data and reconciliation contract for shared Jandal Lists.
>
> **Status:** Authoritative subsystem behaviour spec for issue #1491.
>
> **Applies to:** #1492 sync-ready persistence, #928 two-level hierarchy, #1493 encrypted package exchange, #1494 paired-device convergence, and provider integrations such as #1539.
>
> **Does not define:** any hosted service, production network transport, provider account model, billing, deployment, or commercial packaging.

---

## Principles

1. **Room remains authoritative local state.** Lists UI, skills, widgets, and other local consumers read local persistence, never transport state.
2. **Identity is stable and opaque.** Display names, provider titles, and Room auto-increment IDs are never cross-device identity.
3. **Local-first mutations commit before transport.** A list remains fully usable offline; transport only exchanges recorded state changes later.
4. **Every sync-relevant write uses one atomic persistence seam.** State mutation and change/outbox recording succeed or fail together.
5. **Merge at field granularity where independent intent can coexist.** Editing text and checking the same item on different devices should not erase each other.
6. **Deletion is sticky until explicit restore.** Stale offline edits cannot resurrect deleted data.
7. **Hierarchy is two levels only.** This contract supports #928 without generalising Lists into an arbitrary tree.
8. **Transport is replaceable.** Package exchange, nearby transfer, CalDAV, or another future transport must consume the same contract rather than inventing provider-specific list semantics.
9. **Local presentation and automation stay local.** Pinning, archiving, favourites, device notifications, and local collision aliases do not become shared state by accident.
10. **Prefer the smallest complete model.** No generic CRDT framework, event-sourced database, account graph, or hosted sync protocol is required by this contract.

## Terminology

| Term | Meaning |
|---|---|
| **Collection** | One Jandal list. |
| **Item** | One entry within a collection. |
| **Actor** | One Jandal installation identity used to stamp locally originated changes. |
| **Change** | One idempotent sync-relevant mutation. |
| **Version stamp** | Deterministic Lamport-style stamp used to resolve concurrent writes to the same synchronised field. |
| **Source sequence** | Per-actor, per-collection contiguous number used to checkpoint delivery of that actor's changes for one collection. |
| **Tombstone** | Persisted deleted state retaining stable identity and deletion metadata. |
| **Restore** | Explicit mutation that reactivates a tombstoned identity. |
| **Placement** | The item's requested parent relationship and sibling order treated as one synchronised field. |
| **Effective hierarchy** | Deterministic two-level hierarchy derived from all reconciled requested placements in a collection. |
| **Canonical title** | Shared collection title that participates in sync. |
| **Local display alias** | Device-local generated name used only when the canonical title would collide with another local list display name. |
| **Checkpoint** | Collection-scoped per-actor delivery position used for incremental exchange. |

## Stable identity

### Identifier types

Use opaque UUIDv4 strings for the first implementation:

- `collectionId`
- `itemId`
- `changeId`
- `actorId`
- `packageId`
- `keyId`
- `memberId`

An equivalent locally generated opaque identifier may replace UUIDv4 only if it preserves the same properties without central allocation.

### Local Room IDs

Existing Room `Long` IDs remain valid local primary/foreign keys for efficient local storage and navigation. They are implementation details.

A local Room ID:

- must not leave the device as collection/item identity;
- must not be used to match imported or remote records;
- may be regenerated by migration/restore without changing sync identity.

### Names are not identity

Two collections with the same title are distinct unless their `collectionId` is the same.

Two items with the same text are distinct unless their `itemId` is the same.

Text/name matching may be used for user search, never reconciliation.

## Actor clocks and change sequencing

The contract uses two monotonically increasing counters with different jobs and scopes.

### Lamport logical clock

Each actor persists one actor-global `logicalClock`.

When creating any local sync-relevant mutation:

1. increment `logicalClock`;
2. use the resulting value in the mutation's `VersionStamp`.

When receiving a remote version stamp with clock `R`:

`logicalClock = max(logicalClock, R) + 1`

before creating any subsequent local sync-relevant mutation.

A version stamp is:

```text
VersionStamp(
    logicalClock: UInt64,
    actorId: UUID
)
```

Comparison is lexicographic:

1. greater `logicalClock` wins;
2. if equal, compare canonical `actorId` strings as deterministic tie-breaker.

Wall-clock `createdAt`/`updatedAt` values do not decide conflicts.

### Per-actor, per-collection source sequence

Each actor separately persists a contiguous `sourceSequence` **for each collection it changes**.

Every locally originated `Change` increments only the source sequence for that change's `collectionId`.

`sourceSequence` is used for collection-scoped incremental delivery/checkpoints, not conflict resolution. Keeping it separate from the actor-global Lamport clock avoids gaps when a device observes a remote clock far ahead of its own, while scoping it to the collection avoids gaps caused by unrelated changes to other lists.

For example, if one actor changes collection X, then collection Y, then X again, X's changes are sequence 1 and 2 for X; Y has its own independent sequence 1.

A change therefore carries:

```text
changeId: UUID
collectionId: UUID
actorId: UUID
sourceSequence: UInt64
stamp: VersionStamp
```

`changeId` is the idempotency key. `(collectionId, actorId, sourceSequence)` is the incremental-delivery coordinate.

## Synchronised collection state

A collection has the following transport-independent shared state:

```text
SharedCollectionState
- collectionId
- canonicalTitle + titleStamp
- lifecycle + lifecycleStamp
- createdAt
```

`createdAt` is immutable presentation metadata, not conflict authority.

### Collection lifecycle

`lifecycle` is either:

- `ACTIVE`
- `DELETED`

Deleting a collection tombstones the collection. It does **not** synthesize individual deletes for every item.

While a collection is deleted:

- the collection and its items are hidden from normal active Lists UI;
- contained item state remains persisted;
- item changes do not implicitly restore the collection.

A later explicit `RESTORE_COLLECTION` with a newer lifecycle stamp reactivates the collection. Items independently tombstoned before or after collection deletion remain tombstoned.

This makes list restore safe and avoids a destructive cascade in the shared model even if current local Room storage previously used FK cascade for hard deletion.

## Synchronised item state

An item has these shared fields:

```text
SharedItemState
- itemId
- collectionId
- text + textStamp
- checked + checkedStamp
- dueAt + dueAtStamp
- placement(parentItemId, orderKey) + placementStamp
- lifecycle + lifecycleStamp
- createdAt
```

`dueAt` may be null.

`parentItemId` may be null.

`createdAt` is immutable presentation metadata and may be populated from first-seen time only when an importing adapter genuinely has no source creation metadata.

### Why placement is one stamped field

`parentItemId` and `orderKey` are one logical user action when an item is moved/reparented.

They must therefore share one `placementStamp`.

Stamping parent and order independently can produce a merged placement that no user made—for example, the parent selected by one concurrent move combined with the sibling position from another parent group. Treating them atomically avoids that invalid cross-merge while remaining much simpler than a sequence CRDT.

## Device-local state

The following current Jandal fields are local-only:

### Collection-local

- pinned state;
- archived state;
- local overview display order;
- generated local display alias.

### Item-local

- favourite state;
- notification/alarm time.

These values:

- do not appear in shared snapshots or sync changes;
- do not participate in conflict resolution;
- are never inferred from another device's values.

### Neutral defaults on import

When a shared collection/item is first created locally:

- collection `pinned = false`;
- collection `archived = false`;
- collection is appended to the device's local overview order;
- item `isFavourite = false`;
- item `notificationTime = null`;
- local display alias is null unless a local name collision requires one.

Future issues may explicitly promote a local-only field to shared state, but that requires a contract change.

## Canonical title and local display alias

Jandal needs unique, understandable local list names while shared/provider collections may legitimately have duplicate titles.

The contract separates:

- **canonical title:** shared/synchronised;
- **local display alias:** generated, local-only.

### Collision rule

When importing/binding a new collection whose canonical title conflicts with an unrelated local effective display name:

1. do not merge by title;
2. do not rename the shared/remote collection;
3. allocate a unique local alias;
4. keep sync operating against the unchanged canonical title;
5. avoid blocking the import with a conflict-resolution dialog.

Preferred alias shape:

```text
<canonical title> (<source label>)
<canonical title> (<source label> 2)
<canonical title> (<source label> 3)
```

Examples:

```text
Shopping (Imported)
Shopping (Nextcloud)
Shopping (Nextcloud 2)
```

The concrete source label belongs to the importing transport/provider; the core contract only requires a deterministic unique alias.

### User messaging

A collision may produce one lightweight informational message with an optional Rename action. It must not repeatedly interrupt sync.

### Explicit rename

Jandal does not introduce a separate user-editable "local alias" feature in this workstream.

If the user explicitly renames a shared/bound list, that is a real shared rename:

- update canonical title through the normal mutation seam;
- clear any generated local alias;
- if the requested effective local name still collides, apply normal local uniqueness handling rather than merging identities.

### Remote rename into a collision

If a remote canonical rename creates a new local collision:

- accept the canonical shared title according to normal conflict rules;
- generate/update the local alias;
- do not reject or push an artificial rename solely to satisfy local uniqueness.

If the collision later disappears, an automatically generated alias may be cleared because it has no user-authored semantics.

## Change model

All sync-relevant mutations use explicit changes.

### Collection changes

```text
CREATE_COLLECTION
SET_COLLECTION_TITLE
DELETE_COLLECTION
RESTORE_COLLECTION
```

### Item changes

```text
CREATE_ITEM
SET_ITEM_TEXT
SET_ITEM_CHECKED
SET_ITEM_DUE_AT
SET_ITEM_PLACEMENT
DELETE_ITEM
RESTORE_ITEM
```

`SET_ITEM_PLACEMENT` carries both `parentItemId` and `orderKey`.

### Common change envelope

Conceptually:

```text
Change
- formatVersion
- changeId
- collectionId
- targetId
- actorId
- sourceSequence
- stamp
- operation
- payload
```

The implementation may use sealed Kotlin types rather than a generic map. The wire/package representation must remain explicitly versioned.

### Create semantics

Create establishes stable identity and initial field values.

A repeated create for an already-known stable identity is idempotent when compatible with existing state. If a package attempts to reuse a known stable identity for a structurally incompatible object, reject that input as invalid rather than creating a duplicate identity.

### Idempotency

Persist applied `changeId` knowledge sufficient to ensure a duplicate delivery has no effect after first application.

A duplicate change:

- must not create a duplicate row;
- must not advance a field stamp again;
- must not trigger a second hierarchy cascade;
- must not create a second outgoing copy of the same logical mutation.

## Conflict semantics

### Independent additions

Different stable `itemId` values always remain distinct even when text is identical.

### Independent fields

Each synchronised scalar field has its own version stamp.

Example:

- Actor A edits `text`.
- Actor B checks the same item.

Both survive because `text` and `checked` are reconciled independently.

### Same-field conflicts

For concurrent writes to the same field, apply the value with the greater `VersionStamp`.

This rule covers:

- collection title;
- item text;
- checked state;
- due date;
- placement.

### Reorder/reparent conflicts on the same item

Because placement is one stamped field, a concurrent move conflict on the same item chooses one complete `(parentItemId, orderKey)` placement rather than mixing half of each move.

Cross-item placement conflicts that can create an invalid hierarchy are resolved by the deterministic hierarchy normalisation below.

### Delete versus ordinary changes

Deletion is **sticky**.

Once lifecycle is `DELETED`:

- ordinary field changes do not reactivate the object;
- stale or even numerically later non-restore changes cannot implicitly resurrect it;
- only explicit restore may clear deletion.

An implementation may retain otherwise valid later field values for diagnostics/retry, but normal state application must not make them visible while the tombstone is active.

### Restore

`RESTORE_ITEM` or `RESTORE_COLLECTION` changes lifecycle back to active only when its lifecycle stamp is greater than the current lifecycle stamp.

After restore:

- the object uses its retained pre-delete field state;
- subsequent explicit field changes apply normally;
- a later delete with a greater lifecycle stamp deletes it again.

### Collection delete versus item changes

A deleted collection suppresses all contained items regardless of individual item lifecycle.

An item change received while its collection is deleted does not restore the collection.

### No wall-clock last-write-wins

`updatedAt`, device time, server receive time, file modification time, or transport order must never override the version-stamp rules.

## Two-level hierarchy contract

#928 owns hierarchy UX and behavioural rules. This spec owns the transport-safe representation.

### Valid relationships

An item's **requested placement** is either:

- top-level: `parentItemId = null`; or
- child candidate: `parentItemId` references another item in the same collection.

The **effective hierarchy** rendered and exposed to local consumers must always be acyclic and no deeper than two levels.

An item that already has effective children cannot also be an effective child. Concurrent cross-item placement changes can temporarily produce requested placements that violate this invariant, so validity cannot depend on whichever change happened to arrive first.

### Deterministic cross-item hierarchy normalisation

After ordinary per-item placement-stamp reconciliation, derive the effective hierarchy from the complete current set of requested placements for the collection.

For all active items whose requested `parentItemId` refers to an active item in the same collection:

1. create one candidate edge `child -> parent` carrying the child's `placementStamp`;
2. sort candidate edges by **descending `placementStamp`**;
3. for an exact stamp tie, sort by lexicographically ascending child `itemId`, then ascending parent `itemId`;
4. process candidates in that fixed order and accept an edge only when all of these remain true:
   - child and parent are different items;
   - adding the edge does not create a cycle in the already accepted graph;
   - the parent has no accepted parent, so the parent remains top-level;
   - the child has no accepted children, so the child does not become both parent and child;
5. suppress any candidate that fails those checks from the **effective hierarchy** and render that child as top-level using its existing `orderKey` plus stable `itemId` tie-breaker.

The requested placement register and its stamp are retained; normalisation is a deterministic derived view, not a synthetic sync write. This is necessary so every peer with the same reconciled requested placements computes the same effective two-level forest regardless of delivery order. A later explicit placement change writes a newer placement stamp and therefore changes the candidate set/priority normally.

This rule resolves, for example:

- concurrent `A -> B` and `B -> A`: the higher-priority candidate by the ordering above is accepted and the other is effectively top-level;
- concurrent changes that would produce `grandparent -> parent -> child`: candidate priority deterministically decides which relationship is retained so effective depth never exceeds two.

Do not emit an additional repair change solely because a candidate is suppressed. Transport/package snapshots carry the requested placement registers and stamps; every receiver derives the same effective hierarchy using this rule.

### Missing parent during delivery

Transport ordering must not hide data.

If a child's requested parent is not yet present/active:

- persist the requested placement;
- render/treat the child as temporarily top-level for safe visibility;
- include the edge in normalisation once the parent exists and is active.

### Deleted parent

#928 requires deleting/capturing a parent to preserve its children.

Before/with parent deletion, the authoritative mutation seam records explicit `SET_ITEM_PLACEMENT` changes that promote affected children to top level with deterministic order, then records the parent deletion.

If delivery order temporarily exposes a child whose parent is already tombstoned, the child is rendered top-level until its promotion change arrives.

### Completion cascades

Hierarchy completion behaviour is normal list behaviour, not a separate sync protocol.

If a user action or imported/provider mutation causes #928 to derive additional checked-state changes—for example, completing all children causes the parent to complete—each resulting checked-state mutation receives its own normal change identity/stamp.

The authoritative mutation seam must avoid feedback loops: applying a known change idempotently cannot continually regenerate equivalent derived changes.

## Sync-safe sibling ordering

### Order key

Each item placement includes a canonical arbitrary-precision decimal `orderKey`.

Compare keys numerically using arbitrary precision, then use stable `itemId` as deterministic tie-breaker.

Examples:

```text
append after 5       -> 6
between 5 and 6      -> 5.5
between 5 and 5.5    -> 5.25
```

Top-level items and each parent's child group form independent sibling sequences after effective hierarchy normalisation.

### Reorder operation

A user move emits `SET_ITEM_PLACEMENT(parentItemId, orderKey)` for the moved item.

Do not routinely renumber every sibling after one drag.

### Precision

The first implementation may store the canonical decimal form as text if that avoids lossy SQLite floating-point representation, provided comparisons use exact decimal semantics in the authoritative ordering path.

No fixed precision limit or background rebalance protocol is introduced by this spec.

If real implementation evidence later demonstrates pathological key growth, handle that in a targeted follow-up without replacing the overall sync model.

## Tombstone retention and compaction

### First implementation

Do not automatically garbage-collect shared tombstones.

This is intentional: deleting tombstones before all possible stale peers have advanced can allow old state to return as apparently new data.

### Bounded change log is separate

Keeping tombstones does not require keeping every historical change forever.

The outbox/change history may be compacted once a current full snapshot can represent equivalent state.

### Future compaction

A future issue may define safe tombstone expiry only after it has a concrete peer/checkpoint policy that proves stale resurrection cannot occur.

A user-facing Trash/Recently Deleted UI is separate product UX and is not required by this contract.

## Snapshot and incremental exchange

Room current state is authoritative. The change log is a sync aid, not the database of record.

### Full snapshot

A full collection snapshot contains:

- shared collection state;
- all current shared item state, including requested placement registers/stamps;
- required item/collection tombstones;
- field/version stamps;
- current per-actor delivery checkpoint information **for this collection**.

Local-only state is excluded. Effective hierarchy is derived from the shared requested placements after reconciliation.

### Checkpoint

A checkpoint is scoped to one `collectionId` and records the delivery position for each origin actor within that collection:

```text
Checkpoint(collectionId)
actorId -> highest contiguous sourceSequence applied for this collection
```

Because `sourceSequence` is both separate from the actor-global Lamport clock and scoped to `(actorId, collectionId)`, sequence numbers are contiguous for one actor's changes to that collection even when the same actor changes other collections between them.

### Incremental exchange

A sender may provide changes for the package/bound collection newer than the receiver's checkpoint for that same collection.

The receiver:

1. verifies package/change format and matching `collectionId`;
2. ignores already-applied `changeId` values;
3. applies new changes through the authoritative mutation/reconciliation seam;
4. advances that collection's per-actor checkpoint only across contiguous applied source sequences for the same `(actorId, collectionId)`.

Changes belonging to another collection are never required to fill a checkpoint gap for this collection.

### Snapshot fallback

If the sender no longer retains enough historical changes for this collection to satisfy the receiver's collection-scoped checkpoint, send a fresh full snapshot for that collection.

Snapshot reconciliation uses the same stable IDs, field stamps, lifecycle semantics, requested placements, and deterministic effective-hierarchy normalisation as incremental changes.

### Change-log compaction

After a durable current snapshot can represent state and required delivery guarantees are met, historical change rows may be compacted.

This spec does not require a permanent event log.

## Encrypted shared-package boundary

#1493 will implement package UX. This spec defines only the interoperable client-side boundary.

### Envelope

Conceptual structure:

```text
SharedCollectionPackageV1
- formatVersion = 1
- packageId
- collectionId
- keyId
- nonce
- ciphertext
```

The plaintext envelope must not contain:

- collection title;
- item text;
- checked state;
- due date;
- hierarchy;
- other user list content.

### Ciphertext payload

The encrypted payload contains:

```text
SharedCollectionPayloadV1
- collection snapshot and/or incremental changes
- tombstones/lifecycle state
- field/version stamps
- collection-scoped checkpoint
- minimum membership metadata
```

### Authenticated encryption

Preferred first implementation:

- AES-256-GCM;
- random 256-bit collection key;
- fresh 96-bit nonce per encrypted package;
- envelope metadata that must be tamper-evident included as authenticated additional data where practical.

Never reuse a nonce with the same key.

### Invite/secret capability

The encrypted package references `keyId`; it does not expose the collection key in public envelope metadata.

A separate secret invite/capability representation carries the minimum recipient material:

```text
SharedCollectionInviteV1
- formatVersion
- collectionId
- memberId
- role
- keyId
- collectionKey
```

First-slice role semantics need only the permissions genuinely required by #1493; do not build a general account/social graph.

How the secret capability is transported, rotated, revoked, hosted, or monetised is out of scope.

### Validation

Before mutating Room, import must validate:

- supported format version;
- required identifiers;
- authenticated decryption;
- payload structure;
- stable-identity consistency.

Corrupt, incompatible, or undecryptable packages fail without partial list mutation.

### First-slice package vehicle (#1493)

The first implementation exchanges packages as one user-transported text file:

```text
<file format version = 1>
SharedCollectionInviteV1   — collection, member, role, keyId, collection key
SharedCollectionPackageV1  — packageId, collection, keyId, nonce, ciphertext
```

- The invite travels inside the same file because the transport is the user's own file sharing.
  Whoever holds the file can open and edit the bound list; the export confirmation says so.
- Each export generates a fresh 256-bit AES-GCM key and a fresh 96-bit nonce, and `keyId` is a
  truncated hash of that key, so the invite's key can be checked against the envelope before any
  decryption work and a nonce is never reused under a key.
- Authenticated additional data is the envelope metadata `formatVersion|packageId|collectionId|keyId`,
  so retargeting a package at another collection, another package identity or another key fails
  authentication rather than merging.
- Import validates in order: file structure and versions, invite/envelope agreement, key identifier,
  authenticated decryption, payload structure, and stable-identity consistency. Only then does one
  Room transaction apply the snapshot, so a rejected package changes nothing.
- Applying a snapshot uses the same stamp, lifecycle, placement and ordering rules as incremental
  changes. Imported values are remote state rather than new local edits, so they record no local
  change; a completion cascade the merge itself causes still records its normal explicit change.
  Checkpoints merge per `(collectionId, actorId)` by highest contiguous sequence, and a package for
  one collection never carries another collection's delivery positions.
- Device-local fields keep the device's own values, and a collection created by an import uses the
  neutral defaults above. Re-importing an unchanged package merges to no change.
- Entry points: **Export Jandal file** from either the Lists overview row overflow or the list detail
  overflow (the same encrypted package implementation); **Import Jandal file** from the Lists
  overview overflow.

Key hosting, rotation, revocation, accounts and any transport other than the user's own file
sharing remain out of scope.

## Authoritative mutation seam rules

The #1492 seam is responsible for more than database convenience. It is the correctness boundary for all later transports.

For a local user/skill mutation it must:

1. resolve current stable identity/state;
2. increment the actor-global logical clock and this collection's source sequence as required;
3. create the explicit change(s);
4. update current Room state and outbox/applied-change metadata atomically;
5. trigger existing local observers only after successful persistence.

For an imported/remote change it must:

1. validate format/stable identity and collection scope;
2. advance local actor-global Lamport clock from observed stamps;
3. check `changeId` idempotency;
4. apply field/lifecycle/requested-placement conflict rules;
5. derive the effective hierarchy using the deterministic cross-item normalisation rule rather than arrival-order rejection;
6. persist current state and applied-change/collection-checkpoint metadata atomically;
7. allow normal Room observers to update UI/skills/widgets.

Transport code must not write List entities around this seam.

## Failure behaviour

### Invalid identity/reference

Reject malformed changes that:

- reference no collection;
- reuse an identity for an incompatible object;
- attempt a parent relationship across collections.

Do not partially apply the invalid change.

Same-collection cycle/depth conflicts produced by otherwise valid concurrent placements are **not** rejected based on arrival order; they are resolved by deterministic effective-hierarchy normalisation.

### Missing parent

Not fatal. Preserve the requested relationship metadata and show the child safely as top-level until resolvable.

### Name collision

Not fatal. Generate a local alias; never merge by name.

### Unsupported package version

Reject before mutation with a truthful incompatibility error.

### Duplicate package/change

No-op after first successful application.

### Local transaction failure

Do not leave state changed without its corresponding outbox/change record.

### Transport failure

Does not roll back an already committed local mutation. Pending work remains locally recordable for later delivery.

Must prove:

- stable ID migration/persistence;
- actor-global Lamport clock plus per-collection source-sequence persistence;
- field-stamp comparison;
- atomic mutation + outbox recording across all known writers;
- tombstone/restore behaviour;
- local alias persistence;
- sync-safe requested-placement storage and deterministic effective-hierarchy derivation.

### #928 hierarchy

Must prove:

- two-level constraint;
- placement/reparent/unparent behaviour;
- parent completion rules;
- parent delete/capture preserves children;
- hierarchy changes use the authoritative mutation seam.

### #1493 encrypted package exchange

Must prove:

- authenticated package round-trip;
- hierarchy/order preservation;
- tombstone/restore preservation;
- collision alias handling;
- duplicate import idempotency;
- local-only neutral defaults;
- collection-scoped checkpoints do not depend on changes from other collections.

### #1494 paired-device convergence

Must prove:

- independent additions;
- independent field edits;
- same-field conflict;
- delete versus stale edit;
- explicit restore;
- hierarchy and sibling-order convergence;
- duplicate delivery;
- offline/reconnect;
- one actor can interleave changes across two collections without either collection's incremental checkpoint stalling;
- concurrent `A -> B` and `B -> A` placements converge to the same acyclic effective hierarchy on both devices;
- concurrent placements that would otherwise create depth greater than two converge to the same effective hierarchy;
- the same conflicting placement set applied in different delivery orders produces identical effective hierarchy and normalized list state.

### Provider integrations such as #1539

Must translate provider state into this contract and back without creating a second identity/conflict model.

Provider metadata such as remote UID, href, ETag, account identity, or collection URL belongs in provider-binding state, not in Jandal stable IDs.

## Explicit non-goals

This contract does not define:

- production internet transport;
- hosted relay/service APIs;
- provider-specific authentication;
- billing, subscriptions, entitlements, pricing, or commercial packaging;
- general user accounts or contact/social graphs;
- hierarchy deeper than two levels;
- user-facing Trash/Recently Deleted UI;
- notes, memory, chat, profile, or attachment sync;
- a generic CRDT library;
- a permanent event-sourced Lists database;
- transport logic in widgets or Compose screens;
- automatic tombstone garbage collection;
- provider-specific ordering extensions.
