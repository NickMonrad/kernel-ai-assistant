# #1557 Kokoro on ExecuTorch: spike evidence

Debug-only spike (`Refs #1557`). CPU/XNNPACK, fp32, shipped software-mansion dynamic `.pte` pair, debug lane only.
Compared with the Inflect Micro ONNX baseline (#2088, S23U, ORT 1.24.3).

**Verdict: no-go as a selectable voice.** Keep as a debug test lane. Speed (RTF 0.70–0.94 on the S23U, against ~0.24 for Inflect) rules out playback; see "Decision" below.

## Build and gating

- The phonemis JNI is built only with `-Pkokoro.phonemis=true`. Default off, so CI and release never run CMake or
  package `libkokoro_phonemis.so`. With the property on, the library is configured for debug variants only; release
  configure and build tasks are disabled (`app/build.gradle.kts`).
- Sources are pinned by commit (`app/src/debug/cpp/CMakeLists.txt`): phonemis `5ec260e33127de044bda7147f52cea27a7e2e491`,
  Verbalis `b14f1b3f96e759326935de12f81b35b87ec57f6a` (tag `v0.1.1`). Fetched by CMake `FetchContent`, not from a home directory.
- With the property on, the debug build compiles the library for all four ABIs (no `abiFilters` change; the debug
  arm64-only filter was removed from this PR).
- Off by default, the debug APK adds no native library. Release is unchanged. No `abiFilters` change ships.

## Decisions

- **Model.** Shipped dynamic `.pte` pair, used at exact token length (`n = phonemes + 2`) with an all-true BOOL mask. No re-export. A static no-delegate re-export was dropped.
- **BOOL input.** The 1.5.1 AAR has no BOOL path in `Tensor.ones/zeros/fromBlob`. The runtime rejects UINT8 for a BOOL input (`Input 1 has unexpected scalar type: expected Bool but was Byte`). Route used: `BoolInputTensor`, a Java subclass of `org.pytorch.executorch.Tensor` that overrides `dtype()` and `getRawDataBuffer()`. No JNI is added to ExecuTorch. A Kotlin subclass does not compile (`Tensor(long[])` is `internal`).
- **BOOL output.** Removed. The 1.5.1 AAR builds no BOOL output tensor, so a BOOL output would reach `Tensor_unsupported` and throw. Only BOOL input is supported.
- **Reliance on undocumented behaviour.** `BoolInputTensor` depends on two 1.5.1 JNI reads (dtype via `dtypeJniCode()`, which calls `dtype()`, and `getRawDataBuffer()`). Named in `docs/architecture/executorch-runtime.md` upgrade checklist.
- **Deadline.** Each debug baseline run has a 20 min deadline. On timeout the failure JSON is written and the lane is *not* closed, because `close()` waits on the stuck run's lock. The service then stops and accepts new runs, but the stuck thread and the unclosed model stay in the process, so a later run in that process is not a clean measurement; force-stop before measuring. Not exercised on device (no run has timed out).

## PC evidence

- Static no-delegate vs shipped dynamic (phrase 1): SNR 25.34 dB. Path dropped. Its scripts are not in this PR.
- XNNPACK static duration lowering hung on executorch 1.5.1 (>11 min) and 1.4.1 (1200 s timeout). Path dropped.
- Padded (n=128, valid-prefix mask) vs exact-length all-ones mask, shipped `.pte` (`scripts/verify_unpadded.py`, `scripts/snr_pad_vs_exact.py`): durations identical for phrases L=16, 51, 7. Audio SNR 42.20 dB (phrase 1), 31.76 dB (phrase 2, marginal), 39.37 dB (phrase 3).
- BOOL smoke PTE generated by `core/executorch/tools/generate_bool_smoke_pte.py`. PC runtime: mixed mask `[True,False,True,False]` gives `[1,0,3,0]`.

## Device evidence (S23U, SM-S918B, Android 16)

- `BoolInputSmokeTest`: 3/3 pass on the S23U under the device lock (mixed mask `[1,0,3,0]`, all-true, UINT8 rejected before native code).
  Gradle also ran the same test on the S21 (SM-G991B) during that command. The S21 was **not** locked for it; the S21's state at that time is unknown. Treat as a disclosed, unlocked run.
- Corpus: 8 samples, 3 repeats = 24 rows per run (sha256 `d3f0422e…`, same as #2088). Raw JSONs in `results/`.
- Build: the device APK was built from a dirty worktree on top of `03edad83`. Its debug build still had the arm64 filter and the pre-fix `DebugTtsBaselineService` (no close-after-timeout guard). This PR's code differs from that build in the ways listed under "Code changed after the device runs". **Those runs were not repeated after the fixes.**

Run scripts: `scripts/run_cold.sh <label>` (force-stops and relaunches the app before each run), `scripts/run_warm.sh <label>` (does not force-stop, so E4B stays loaded from the chat warm-up). Neither script takes the device lock; any locking during those runs was manual and is not recorded by the scripts. Paths under `~/.cache/kokoro-et-1557` (not self-contained).

### Kokoro with E4B loaded, warm (one chat message to load E4B, then runs in that process; `run_warm.sh`)

The result files are named `with-e4b-cold1..3`; the "cold" in those names is historical. These are warm runs, not fresh-process runs.

| Run | RTF median (min–max) | First-chunk median | Cancel return | VmHWM end | RSS start |
|---|---|---|---|---|---|
| warm 1 | 0.698 (0.651–0.827) | 2539 ms | 635 ms | 2.33 GB | 1.91 GB |
| warm 2 | 0.939 (0.700–1.106) | 2833 ms | 789 ms | 2.33 GB (inherited) | 1.24 GB |

- **VmHWM 2.33 GB is one measurement** (run 1: 1.92 → 2.33 GB). Runs 2–3 start with `VmHWM` equal to run 1's peak, so their end value is inherited, not measured.
- **E4B residency in runs 2–3 is unverified.** RSS at start falls 1.91 → 1.24 → 0.76 GB, so the model may have been unloaded or partly paged out. The logcat captured for these runs (`results/*.logcat.txt`) is empty, so this cannot be confirmed from the logs. Treat runs 2–3 as "E4B state unknown".
- The RTF rise in runs 2–3 is not explained. The earlier "E4B contention" explanation is not supported: run 1 (the fastest with-E4B run, 0.698) is faster than every alone run. Thermal state was not recorded; heat (the alone runs also drift upwards, 0.75 → 0.85 → 0.86) fits at least as well. Not isolated.

### Inflect baseline (#2088, same device, ORT 1.24.3)

RTF median ~0.24, first-chunk median ~2.5 s, cancel→throw ~5.9 s, VmHWM ~1.02–1.04 GB. #2088 states that the chat model's residency was "not measured or controlled". The baseline therefore does not say whether E4B was loaded, so no Kokoro+E4B vs Inflect memory comparison is made here.

## RTF and timing definitions (Kokoro lane)

- `RTF = synth_ms / audio_ms`. `audio_ms` includes the pause silence the lane appends after each chunk (up to 375–600 ms per chunk, `KokoroEtDebugLane.kt`) after silence stripping. Pauses count as audio, which lowers RTF. Speech-only RTF would be somewhat higher.
- Durations above the 296-tick program bound are scaled down silently by the lane (`scaleDurations`). Scaling is not recorded in the JSON, so the frequency is unknown.
- `first_chunk_ms` = frontend + first chunk synthesis, as in #2088.
- Cancel probe: 1000 ms cancel on the longest sample. Kokoro checks cancel between chunks; Inflect checks at its stage boundaries. The cancel numbers are not like-for-like.

## Comparison (with the caveats above)

- Kokoro alone: RTF 3.1–3.6× the Inflect median; first-chunk similar (2.5–3.1 s vs 2.5 s); cancel return faster (~0.65 s vs ~5.9 s, different cancel points).
- Peak RSS: Kokoro alone ~1.3 GB VmHWM vs Inflect ~1.0 GB, with a 331 MB fp32 model pair on disk.

## Decision

Keep Kokoro as a debug-only lane. Do not offer it as a selectable voice. Revisit only after: a quantised XNNPACK export is measured; the lane runs on the S21 too; E4B residency is verified per run (VmHWM reset via `clear_refs`, RSS checked at start); thermal state is recorded; the RTF definition is decided (speech-only and with-pause).

## Known defects and gaps

- **Digit normalisation (fixed in #2115).** "It happened in 1999." now reaches the phonemiser as "It happened in nineteen ninety nine." through the shared `EnglishSpeechTextNormaliser`. Before #2115 it phonemised to `ˌɪt hˈæpənd ɪn nˌIntˈin nˈIndinˈIn`.
- **Listening set not done.** 16 WAVs rendered on PC (not device output) to `/home/lokhor/private-acoustic-fixtures/kokoro-executorch-1557/` (outside the repo, not uploaded). Not listened to, not ASR-checked.
- **Phrase 2 PC equivalence marginal** (31.76 dB).
- **Dead work.** `NativeKokoroPhonemizer.kt` computes `words` that the lane never uses. Not removed in this PR.
- **16 KB and APK size not re-run.** `scripts/check_android_16kb_artifacts.py` needs an AAB and bundletool; not built here. With the property off, the APK adds no native library. With it on, debug builds add `libkokoro_phonemis.so` and the phonemis/Verbalis static code; those figures are unmeasured.
- **Error path.** A UINT8 BOOL input hung the lane for ~15 min (no JSON, no exception) on the S23U. The Kotlin dtype pre-check now rejects it before native code; the deadline writes a failure JSON on timeout. The deadline path has not been run on device.
- **Release phonemiser licence** undecided (above).

## Code changed after the device runs

The device runs used a build that predates these changes; none was repeated on device:
- `DebugTtsBaselineService`: no `close()` after a deadline timeout; the `KOKORO_ET` lane factory branch was committed in this PR.
- `NativeModule.kt`: BOOL output branch removed (`DType.BOOL` now throws `ExecuTorchException`); `Bool.fromOutput` and the output-doc line removed.
- `app/build.gradle.kts`: debug `abiFilters` removed; CMake gated behind `-Pkokoro.phonemis=true`; release CMake tasks disabled when the property is on.
- `CMakeLists.txt`: home-directory source removed; phonemis and Verbalis pinned by commit.
- Stale comments fixed (`KokoroEtDebugLane.kt`, `KokoroTts.kt`).

The BOOL input path (`BoolInputTensor`) is unchanged, and `BoolInputSmokeTest` still passes on the S23U from before these changes (not re-run after).
