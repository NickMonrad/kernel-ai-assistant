## Summary

- **The epic's "Measurement correction" is wrong.** The 18 Nov figures it re-labels as raw decoder WER were PCEC-corrected all along. The mislabel started with a Sol review instruction. Sol later had code evidence of the error, but never corrected the epic or #1978 bodies (F1).
- **#1987 went through about 26 review rounds in 55 h without converging.** It grew from an engine addition into a 44-file, +9,753-line rewrite of shared capture lifecycle code that now includes alarms, wake and the widget. At handoff, the only exact-head device check, an unattended PTT run on build 4421, **failed**. The other checks were not run (F2).
- **None of the benchmark evidence can be reproduced from anything published.** Every #1978/#1988 number comes from commits that exist only on the local disk (F3).
- **The S/c32r8 size/tier recommendation is not decision-grade** (F4).
- **The owner's "start now" for #1923/#1959/#1961 was not followed.** #1995 was paused under the file-overlap rule even though it shares no files with #1987 (F5).
- **#1988 produced no ExecuTorch comparison.** "Insufficient evidence to replace ONNX" was posted to the epic as the runtime recommendation (F6).
- **What held up:** the WER arithmetic reproduces exactly from the private reports, all four report SHA-256 digests match, the timing figures re-derive, and there were no merges or force-pushes. Owner audio stayed out of Git. Sol's #1995 review findings were later confirmed (section 7).

### F1 (High, CONFIRMED). The "raw decoder" label on the 18 Nov WER figures was itself the error, and it is still in the specs

- **Where the label came from.** On 18 Nov at 02:47, Sol review `5b3f17e` said "Label raw-decoder WER as such". It meant the Zipformer rows, which skip the production normaliser. The orchestrator relayed it to harness worker `2ecb999` as "label raw-decoder WER, not shipping-corrected WER". The worker then named the field for **every** lane `raw_decoder_wer`. In the harness at `8425e287` (`Asr4allTierMeasurementDeviceTest.kt:304–305`), that field scored `engine.finish(); val transcript = engine.decodePcec(decodeTail = true)`, which is the PCEC-corrected final.
- **How it spread.** The worker's RESULT comments ([#1978 S23U](https://github.com/NickMonrad/kernel-ai-assistant/issues/1978#issuecomment-6970854960), [#1978 S21](https://github.com/NickMonrad/kernel-ai-assistant/issues/1978#issuecomment-6972306290)) reported "Owner WER (raw decoder)": S 32.88/27.40, M 26.03/26.03, Zipformer 47.26. The owner-side edit of 18 Nov 07:51 added a "Measurement correction (18 Nov 2026)" section to #1977 saying these "are not PCEC-on WER and must not be quoted as the corrected result". #1978 gained "Existing evidence is raw-only".
- **Sol had the evidence.** At 08:27:43 Sol ran `git grep` on `8425e287`. The output showed the PCEC call. In the same batch, Sol posted [#1977 comment 6973200764](https://github.com/NickMonrad/kernel-ai-assistant/issues/1977#issuecomment-6973200764) saying the harness "appears to render PCEC before writing that field. Do not use those values as corrected WER". At 10:08 it told the owner "those scores are diagnostic only".
- **The reruns proved it.** The PCEC-primary reruns at `aee36565` and `add7fe2f` produced **identical** edit counts for S and M (48/40/38/38 of 146) and different raw counts (53/47/42/39). I re-derived both from the private reports.
- **Nobody corrected it.** Neither Sol nor anyone else has corrected the epic or #1978 bodies. Both still tell readers that valid PCEC results are raw.
- **Cost.** The rerun was needed anyway for L, the raw/PCEC split and backlog. The lasting damage is a false statement in the public spec that the owner relied on.

### F4 (High, CONFIRMED). The S/c32r8 recommendation is not decision-grade

The recommendation ([#1977 comment 7030615938](https://github.com/NickMonrad/kernel-ai-assistant/issues/1977#issuecomment-7030615938)) proposes ONNX **S/c32r8** for FLAGSHIP and MID_RANGE, "keep existing recognizer" for LOW_POWER, and L benchmark-only.

- **Accuracy.** S/c32r8 makes 40 edits against M/c16r4's 38 on 146 words. Per clip, 6 are worse, 5 better and 9 tied (sign test p≈1). The 1σ binomial error alone is about ±3.7 pp. Only the gap to Zipformer is robust (69 vs 40 edits, 12/1/7 per clip, p≈0.003).
- **Live text.** At c32r8 a corrected partial appeared on only **11/20** clips for S, M and L on both phones. On 9 of the owner's 20 utterances the user would see no streaming text before the final. #1978 criterion 1 makes streaming partials an acceptance requirement. The recommendation mentions "11/20" but does not weigh it.
- **Latency.** Speech-end latency is effectively unmeasured. There are 5 usable VAD references out of 20, and **one** qualifying clip per c16r4/Zipformer lane, the same clip in each. No c32r8 endpoint qualified on either phone (#1978 [comment 7030798300](https://github.com/NickMonrad/kernel-ai-assistant/issues/1978#issuecomment-7030798300)).
- **Memory.** The "405 vs 237 MiB" argument uses whole-process sampled PSS that depends on lane order. For example, on S23U the first lane (S/c16r4) has a warm median of 276 MiB but a peak median of 609, and Zipformer's warm median (612) is higher than L/c32r8's (542). Sol caveats this and then uses it anyway.
- **Contradiction with #1982.** "LOW_POWER: keep existing recognizer" means keeping Zipformer, which #1982 removes.
- **The baseline is not like for like.** Zipformer is scored on raw recogniser output without the app's transcript corrections. Sol's own reviewer flagged this ("the row labeled `shipping` scores raw Zipformer output, omitting production corrections such as `patroni` → `Petone`"), and the final benchmark did not address it. asr4all still wins, but the 47.26% baseline overstates the gap users would see. Direction CONFIRMED; size of the effect PLAUSIBLE.

### F6 (High; facts CONFIRMED, interpretation PLAUSIBLE). #1988 delivered no comparison but was reported as a recommendation

- **Coverage.** Only S/c16r4 was attempted, on S23U only, with a public clip. Both the Maven and S3 XNNPACK ExecuTorch 1.5.1 builds failed the first-step parity check, with the same Android logits hash. The S21, M, L and all owner clips were never run.

- **It looks like a harness bug.** The Android raw text begins `s'abcdefghijkigsen`, an ordered run of alphabet tokens, yet the step-0 logit deltas against Python are only −0.055 to 0 (mean +0.008). That pattern points to a tensor-layout or decoding defect in the probe rather than the runtime (PLAUSIBLE). Sol's issue comments do say a harness or JNI cause is not excluded; the epic summary does not.
- **The epic gate cannot be met as written.** The epic's "Review the #1988 runtime comparison before locking the default" has no comparison to review. The independent retest now running is the right next step.

### F7 (Medium, CONFIRMED). The speech-end latency effort produced no usable metric

- **Cost.** At least 5 Sol review sessions on the speech-end probe and VAD tooling, plus VAD worker `a0bfeb4` (about 73 M tokens), produced a v5 reference with 5 usable clips out of 20.
- **Root cause.** Sol itself traced it ([#1978](https://github.com/NickMonrad/kernel-ai-assistant/issues/1978)): "The splitter keeps only 50 ms after each internal gap begins." That splitter was written by Sol's #1984 worker. #1984 asked only to "split each section on silence" into clips of 5 s or less, and clips average about 2.8 s, so there was room for 500 ms or more of trailing quiet.
- **Knock-on effect.** The same tight trim stops recognisers from endpointing inside the clip. Of 140 endpoint trials per phone, 105 produced endpoints only after zero post-roll.
- **Why it was not re-cut.** On 18 Nov at 20:48 the owner forbade changing the locked clips, so a re-cut needs an explicit owner decision.
